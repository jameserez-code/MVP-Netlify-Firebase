# Production Use Cases

Each scenario includes: task flow, capabilities required, policies, audit visibility, failure handling, and replay strategy.

---

## 1. Autonomous Coding Agent

**Scenario:** An LLM-based coding agent that writes code, runs tests, and opens PRs for a SaaS team.

**Task Flow:**
1. PM creates task: `{ "repo": "acme/api", "issue": "#342", "instructions": "Fix pagination bug" }`
2. Worker assigns to coding agent (capabilities: `filesystem:read`, `filesystem:write`, `network:http`)
3. Agent clones repo → writes code → runs tests → opens PR
4. Each step is a tool call logged through `/run/:id/log`
5. On success: run completed, PR opened, audit trail has 12 tool calls

**Policy:**
```json
{
  "allowedTools": ["git_clone", "write_file", "run_tests", "create_pr", "read_file"],
  "deniedTools": ["delete_repo", "force_push", "exec_shell"],
  "allowedDomains": [{ "pattern": "github.com", "methods": ["GET", "POST"] }],
  "deniedDomains": ["*.internal-admin.com", "169.254.169.254"],
  "dataRestrictions": { "denySecretsInParameters": true }
}
```

**Audit:** Every file write, test run, and PR creation is logged with parameters, decision, and timestamp. The PR description includes the audit trace ID: "This code was generated by Agent-42 under run sess_a3f... — full trace at /run/sess_a3f/trace"

**Failure handling:** If tests fail → agent retries with backoff. If 3 retries exhausted → task marked failed, operator notified. Replay available: POST /org/seed creates fresh task with same payload.

## 2. Support Automation Agent

**Scenario:** Customer support bot that looks up orders, checks inventory, and responds to tickets.

**Task Flow:**
1. Zendesk webhook → POST /task `{ "ticketId": "ZD-8821", "query": "Customer wants to know order status" }`
2. Agent calls `lookup_order(ZD-8821)` → ALLOW (within policy)
3. Agent tries `send_email(to=customer)` → DENY (blocked by policy — email requires human approval)
4. Agent returns: "Order #42 shipped yesterday. Tracking: UPS-9921. I've flagged this for a human to send the confirmation email."
5. Operator approves email in dashboard → task completed

**Policy:** `send_email` in deniedTools forces human-in-the-loop. The agent cannot autonomously email customers.

**Audit:** The DENY event on `send_email` is logged with reason "tool_explicitly_blocked". Operator can see the denied attempt, approve or override. The enforcement layer prevents data exfiltration even if the LLM is prompt-injected.

**Replay:** Each support ticket has a unique task. Replaying a failed ticket creates a new task with the same payload — the agent retries from a clean state.

## 3. CI/CD Orchestration Agent

**Scenario:** Agent monitors CI pipelines, retries failed builds, notifies teams.

**Task Flow:**
1. GitHub webhook on build failure → POST /task `{ "repo": "acme/web", "buildId": "ci-442", "failure": "Timeout in integration tests" }`
2. Agent capabilities: `network:http`, `task:execute`
3. Agent calls `retry_build(ci-442)` → ALLOW
4. Agent calls `notify_slack(#eng)` → ALLOW
5. Agent calls `access_admin_panel()` → DENY (domain not in allowlist — `*.internal-admin.com` blocked)
6. Build passes on retry → run completed

**Policy:** Admin panel access is explicitly denied via domain blocklist. Even if the agent's LLM hallucinates admin access, the enforcement layer blocks it.

**Audit:** 4 tool calls logged (2 ALLOW, 1 DENY). The DENY event has the full URL that was blocked, confirming it was the admin panel.

**Failure handling:** If retry also fails → task failed. Operator can replay: same build parameters, new execution.

## 4. Internal Tooling Agent

**Scenario:** Agent that queries internal databases, generates reports, and emails summaries to managers. Runs on a schedule.

**Task Flow:**
1. Cron → POST /task `{ "report": "weekly_sales", "recipient": "vp-sales@acme.com" }`
2. Agent capabilities: `network:internal`, `filesystem:read`, `audit:read`
3. Agent calls `query_db("SELECT SUM(revenue) FROM sales WHERE week=...")` → ALLOW (internal network)
4. Agent calls `generate_pdf(data)` → ALLOW
5. Agent calls `send_email(to=vp-sales, attachment=report.pdf)` → ALLOW (`send_email` is ALLOWED in this policy — this agent is trusted)
6. Run completed, report delivered, audit trace shows 3 tool calls

**Policy:** This agent has broader permissions than the support bot because it's an internal tool. The policy is explicit about what's allowed — `send_email` is permitted, but only to `*.acme.com` domains (domain constraint on the email tool).

**Compliance:** Every report generation is logged with who requested it, what data was queried, and where the report was sent. SOC 2 auditor can request the audit trace for any run.

**Replay:** Regenerate last week's report by replaying the task — same query, same output, deterministic reproduction.

## 5. Document Processing Agent

**Scenario:** Agent that processes incoming PDFs, extracts data, validates against rules, and routes to appropriate teams.

**Task Flow:**
1. File upload → POST /task `{ "document": "invoice-442.pdf", "type": "invoice" }`
2. Agent capabilities: `filesystem:read`, `network:http`
3. Agent calls `extract_pdf(invoice-442.pdf)` → ALLOW
4. Agent calls `validate_against_rules(data)` → ALLOW
5. Agent tries `write_to_external_api(data)` → DENY (domain `*.external-vendor.com` not in allowlist)
6. Agent returns: "Invoice processed. Data validated. External API write blocked — requires manual review."
7. Operator reviews, manually posts to vendor API, marks task completed.

**Policy:** External vendor domains are restricted. The agent processes documents internally but cannot autonomously push data to third-party APIs.

**Audit:** The DENY shows exactly which domain was blocked and what data the agent tried to send. This is crucial for compliance — the system prevented an unauthorized data transfer.

**Replay:** Same document can be reprocessed by replaying the task. Useful for testing policy changes: "If we add this domain to the allowlist, does the workflow complete?"

## 6. Compliance-Sensitive Workflow

**Scenario:** Financial services agent that processes transactions, but every write must be explicitly approved.

**Task Flow:**
1. Scheduled job → POST /task `{ "batch": "ACH-2026-05-14", "transactions": 42 }`
2. Agent capabilities: `network:internal`, `audit:read`, `task:execute`
3. Agent calls `read_transactions(ACH-2026-05-14)` → ALLOW (read is always permitted)
4. Agent calls `validate_transactions(batch)` → ALLOW
5. Agent calls `execute_transfers(batch)` → DENY (capability `filesystem:write` not granted — this agent is read-only)
6. Agent flags batch for human approval. Operator reviews, approves transfers via separate system.
7. Task completed. Audit shows: 42 transactions validated, 0 executed (by design).

**Capability enforcement:** The agent was registered with `capabilities: ["network:internal", "audit:read", "task:execute"]`. The `execute_transfers` tool requires `filesystem:write` capability, which this agent doesn't have.

**Policy + capabilities:** Two-layer enforcement — the policy blocks tool calls, and the capability system blocks entire classes of operations. Even if a policy mistakenly allows `execute_transfers`, the capability check blocks it.

**Audit:** Capability denial is logged separately from policy denial. The audit trail shows: "execute_transfers DENIED (missing_capability: filesystem:write)".

**Replay:** Deterministic. The same batch, replayed with the same agent, produces the same result. To change behavior, register a new agent with the required capability.

## Cross-Cutting Patterns

| Concern | Mechanism | Visible in audit |
|---------|-----------|-----------------|
| Data exfiltration prevention | Domain blocklists, PII detection, denied tools | DENY events with specific violation |
| Human-in-the-loop | `send_email` in deniedTools forces approval | Operator dashboard shows pending actions |
| Compliance evidence | Every tool call logged with decision + parameters | GET /run/:id/trace replays full execution |
| Least privilege | Capabilities + policies = two-layer enforcement | Capability denials logged separately from policy denials |
| Deterministic replay | Same payload + same agent → same result | Replay execution, compare outputs |
| Crash recovery | Worker startup reconciliation, exponential backoff retry | Timeline shows retry events with backoff delays |
